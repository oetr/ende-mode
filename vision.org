* Insert at cursor, aka: deslop-insert-at-cursor
- user wants LLM output where his cursor currently is.
   - If the cursor does not select any part of the buffer, use the whole buffer as context (before and after the cursor, marking the part in a way that the LLM understands where to add things).
   - If only some of the buffer is selected, only use that part as context.
   - Text inserted by the LLM is consequtive, and has no gaps.
   - It is important to note where the cursor is---user can highlight a region and move cursor to beginning or to the end of the highlighted region (using C-x C-x).
     - If the cursor is in the beginning, then insert before the highlighted text and add a newline; otherwise insert a newline at the end of it and right after, the LLM text.
   - Highlighted text will not be mutated in this operation.

* deslop-summarize
- summarize the user-highlighted region and open the summary in another buffer.

* deslop-semantic-table
- Turn a large collection into a table I can actually work on, without first forcing everything into a database.
  - Rows can be files, Org headings, functions, tickets, or arbitrary selected chunks; columns are questions or transformations.
  - e.g. For 200 customer reports: affected feature, reproduction conditions, likely duplicate group, and whether we have enough information to act.
  - Each cell retains its source references; uncertain answers remain uncertain, and I can correct them directly.
  - Filter, group, and select rows, then run an operation on that subset: draft replies, extract regression cases, or build a prioritized work list.
  - Computed cells are cached against their inputs, so changing one report does not require processing the whole collection again.
  - This is an interactive bulk-work interface, not a request for the LLM to print a giant Markdown table.

* deslop-lenses
- Edit the same underlying material through different task-specific views.
  - e.g. View a sprawling Org specification as a requirements matrix, a release-scope outline, or a list of decisions grouped by owner.
  - Views retain explicit links to the original passages instead of becoming disconnected generated documents.
  - Editing a requirement in the matrix proposes the corresponding source edit; moving it between releases proposes the relevant scope changes.
  - If an edit has several plausible interpretations, show the alternatives rather than guessing how to write it back.
  - Source changes invalidate affected parts of the view, not the entire workspace.
  - Human-only sources remain read-only through every lens.

* deslop-tradeoff-lab

  - Each alternative gets an isolated workspace and the same explicit requirements, examples, and evaluation budget.
  - Compare observable consequences: public API examples, representative usage, measured checks, omitted requirements, and maintenance implications.
  - I can change a constraint once and have all alternatives reconsidered against it.
  - The result is a navigable comparison of working artifacts, not three persuasive essays or three completion candidates.

* deslop-example-contract
- Turn examples and counterexamples into an executable definition of what I want.
  - I provide representative inputs, desired outputs, and cases that must not match.
  - e.g. Normalize inconsistent bibliography entries, extract structured events from logs, or enforce a project-specific rule that ordinary linters cannot express.
  - The agent proposes boundary cases for me to label, concentrating on cases where different interpretations would produce different behavior.
  - It builds a local transformer or checker and tests it against the accumulated examples.
  - Deterministic code is preferred where possible; genuinely semantic decisions can use the local model, with uncertain cases routed to a review queue.
  - I can run the resulting operation across thousands of items, inspect failures, add counterexamples, and rerun only affected items.
  - Unlike a playbook, the deliverable is a versioned operation with a test corpus, not instructions the agent may interpret differently next time.

* deslop-work-packet
- Make work delegatable even when the recipient does not have my buffers, environment, or accumulated context.
  - Select a concrete task and package the relevant source snapshots, constraints, examples, permitted commands, and acceptance checks.
  - e.g. Hand a contractor one subsystem change without exposing the entire repository, or send a difficult documentation task to an offline local agent.
  - Preview exactly what leaves the workspace; excluded material is not silently summarized into the packet.
  - The packet includes a runnable entry point where practical, so the recipient can reproduce the starting state rather than reconstruct it from chat.
  - Returned work is imported as a changeset tied to the packet's base versions, with acceptance results and unresolved questions.
  - I can issue several packets independently and reconcile their returned work against my current tree, without giving anyone write access to the originals.
  - This is a portable unit of delegated work, usable by another human or agent—not another conversation that only makes sense inside my current session.* deslop-ensemble
- One goal, many minds. Spawn several specialized sub-agents in parallel on the same prompt, each constrained to a single lens: correctness, performance, readability, security, API ergonomics.
  - Each agent produces its own answer independently, with no awareness of the others.
  - The results are presented not as a merged blob but as a structured debate: agreements are collapsed, disagreements are highlighted with the reasoning behind each position.
  - You adjudicate in-place—accept, reject, or annotate each position—and the mode synthesizes a final result that honors your rulings.
  - This is not "show me three candidates" (that is trivial). The agents have different system prompts, different tool permissions, and different stopping conditions. One might refuse a change that another insists on.
  - Useful when you are unsure what you actually value most about a change and want the tension surfaced before you commit.

* deslop-genesis
- Turn a single prose specification into a complete, internally consistent project skeleton: directory tree, file stubs with docstrings, test scaffolds, CI configuration, dependency declarations, and cross-references.
  - Every stub knows about every other stub. A function signature in file A is referenced by the test in file B with the correct import path, even though neither file has implementation yet.
  - You can then fill any node independently with `deslop-insert-at-cursor` or `deslop-write-anywhere`, and the mode maintains the cross-reference graph as you go, flagging when a stub you just wrote contradicts a signature someone else filled.
  - The skeleton is not static. If you rename a module or restructure directories, the mode propagates the change across all stubs, tests, and import paths.
  - Useful for greenfield work where the architecture is decided but the implementation is months away.

* deslop-converge
- Semantic three-way merge of divergent documents, code, or notes—not a line diff, but an intent diff.
  - Give it a common ancestor and two divergent versions (yours and the LLM's, or two branches, or two drafts from different sittings).
  - It produces a merged result that preserves *meaning* rather than text adjacency, and annotates every region where the two versions made incompatible choices.
  - Conflicts are presented as questions: "Version A restructured this section around the failure mode; Version B kept it organized by subsystem. Which axis do you want?" Not "line 47 vs line 52."
  - The output is a single coherent document plus a conflict log you can work through interactively, resolving one semantic disagreement at a time.
  - Files marked human-only are never written to; conflicts involving them are surfaced as proposals only.

- A background mode that watches your editing trajectory and pre-executes the next likely multi-edit sequence in the undo stack, invisible until you need it.
  - If you rename a function in one place, the shadow agent has already renamed it in the twelve other call sites, updated the docstring, and adjusted the import.   - The shadow buffer (accessible via `C-c d s`) shows what it staged and why, so you can inspect the reasoning before accepting.
  - Nothing is applied to the buffer without your explicit undo-into-it action. You are always in control; the shadow only prepares.
