#+TITLE: enslop — refinement of underspecified parts of vision.org
#+PROPERTY: status decided

This file pins down every decision that vision.org left open, so the
implementation (enslop.el) is fully specified. RAG is explicitly out of
scope for v1 (future work).

* Backend
- "local LLM" = any OpenAI-compatible /v1/chat/completions HTTP server
  (LM Studio, llama.cpp server, Ollama all qualify). No CLI subprocesses.
- Variables:
  | variable               | default                                  |
  | enslop-url             | http://localhost:1234/v1/chat/completions |
  | enslop-model           | "local-model"                             |
  | enslop-temperature     | 0.2                                       |
- Requests are async (url-retrieve). No hard client-side timeout in v1
  (future work); a dead server surfaces as a logged, aborted job.
- The LLM call site is a single pluggable variable enslop-llm-function
  (FN MESSAGES DONE). This is what makes the whole mode testable without a
  live server: the ERT suite swaps in a fake.
- On any LLM/HTTP error: the job is aborted, the failure is logged to
  *enslop-log*, the queue continues with the next job.

* Commands and keybindings
- Minor mode enslop-mode + global-enslop-mode. Prefix C-c e:
  | key   | command                 |
  | C-c e i | enslop-insert-at-cursor |
  | C-c e p | enslop-improve-at-cursor |
  | C-c e s | enslop-summarize        |
  | C-c e l | show *enslop-log*       |
  | C-c e q | queue status (message)  |
  | C-c e a | clear queue             |

* enslop-insert-at-cursor (refined)
- Context:
  - active region  -> only the region text is sent,
  - no region      -> the whole buffer is sent.
  - In both cases the insertion point is marked with a literal <CURSOR>
    token inside the sent text.
- Instruction: fixed, customizable via enslop-insert-instruction
  (default: "Write the most natural continuation of the text at the
  cursor position."). No interactive prompt.
- The LLM reply is cleaned (leading/trailing whitespace trimmed) and
  inserted as one contiguous block.
- Insertion rules (refines the vision's start/end cases, adds the middle
  case and the no-region case):
  | cursor position     | insertion                              |
  | at/before region    | TEXT + newline, before the region      |
  | at/after region     | newline + TEXT, after the region       |
  | strictly inside     | newline + TEXT + newline, at the point |
  | no region           | raw TEXT at the cursor                 |
- The highlighted text itself is never mutated (only text is added around
  or inside it).

* enslop-improve-at-cursor (refined)
- Prompt UI: dedicated buffer *enslop-prompt* shown in a right side window
  (0.35 width). If the buffer already exists and holds a draft, it is
  reused as-is. C-c C-c submits, C-c C-k cancels. Submitting with an empty
  instruction does nothing.
- Target: active region, else the whole buffer.
- Response protocol (this is how "the LLM decides whether to keep the
  region or rewrite the buffer" is made concrete): the LLM must answer in
  exactly one of two formats,
      <<<REGION>>>
      <improved region>
  or
      <<<BUFFER>>>
      <improved entire document>
  A reply without a tag is treated as <<<REGION>>>.
- When the <<<BUFFER>>> option is offered:
  - whole buffer fits in the context budget -> whole buffer is sent
    (region marked with <region>...</region> tags), both tags allowed;
  - buffer larger than budget -> only the region plus up to 500 chars of
    surrounding context are sent, and the prompt FORCES <<<REGION>>>
    (the LLM has not seen the elided parts, so a buffer rewrite would be
    lossy);
  - region larger than budget -> the region is split into consecutive
    chunks <= budget and processed sequentially (each chunk's improved
    text is spliced in before the next chunk is requested). Chunk prompts
    also force <<<REGION>>>. If a chunk reply nevertheless carries
    <<<BUFFER>>>, it is applied (best effort) and chunking stops.
- Chunk splitting is by character count (line-boundary splitting is future
  work).

* enslop-summarize (refined)
- Target: active region, else whole buffer. Read-only: the source buffer
  is never modified.
- Output: appended to *enslop-summary* under a header
  "=== <buffer> (<region|whole buffer>) @ <timestamp> ===", then shown in
  a right side window (best effort, ignored in headless sessions).
- Large content (> budget) is summarized by sequential chunk
  summarization with a running summary (compaction):
  sum(chunk1) -> s1; sum(chunk2, s1) -> s2; ...; final = sN.
  Target summary length is suggested to the LLM via enslop-summary-chars
  (default 4000 chars).

* Queue semantics (the core refinement)
- Jobs run strictly one at a time, in FIFO order. Every job is a snapshot
  taken at enqueue time; execution re-locates its target in the buffer,
  which may have been modified by earlier jobs.
- Anchors (captured at enqueue time):
  - region jobs (insert with region, improve, summarize): the exact region
    text plus the original region start position.
  - insert without region: (BEFORE . AFTER) = up to enslop-anchor-chars
    (default 120) characters of buffer text immediately before/after the
    cursor, plus the original cursor position.
- Resolution at execution time (all searches run on the current buffer):
  - region anchor: all occurrences of the anchor text are collected and
    the one whose start is closest to the original position is used
    (handles repeated text better than "first occurrence").
  - cursor anchor, AFTER non-empty:
    phase 1: occurrences of AFTER immediately preceded by BEFORE;
    phase 2 (fallback): all occurrences of AFTER;
    the candidate closest to the original cursor position wins.
  - cursor anchor, AFTER empty (cursor was at buffer end): insert at the
    buffer end (buffer start if BEFORE is also empty).
- Stale jobs: if no anchor occurrence exists, the job is SKIPPED with a
  log + message entry. A job is never applied at a position we cannot
  verify. This answers the vision's open question: an insert queued on a
  region that an earlier improve already rewrote does NOT run silently at
  a wrong place; it is skipped and reported.
- Whole-buffer jobs (improve/summarize queued without a selection) are
  anchored to "the whole buffer", i.e. they always operate on the current
  buffer state at execution time and are never skipped.
- Scenario table (all decided):
  | scenario                                        | behavior                       |
  | 3x insert at the same unselected cursor         | stacked in queue order at that |
  |                                                 | spot (AFTER-anchor falls back  |
  |                                                 | to closest occurrence)         |
  | inserts at disjoint cursors                     | all applied, independent       |
  | insert whose region was consumed by an improve  | skipped + logged               |
  | 2x improve of the same region                   | first applies, second skipped  |
  | improve after an insert at a nearby cursor      | region anchor still found ->   |
  |                                                 | applies (best effort)          |
  | whole-buffer improve queued after an insert     | improves the new whole buffer  |
- C-c e a clears pending jobs; a job already in flight finishes and is
  applied (documented in the command docstring).

* Context management (automatic)
- Budget: enslop-max-context-chars, default 24000 (~6k tokens; tokens are
  estimated as chars/4 — documented approximation, no tokenizer in v1).
- insert: if the context (region or buffer) exceeds the budget, only a
  window of enslop-window-chars (default 8000) chars on each side of the
  cursor is sent, with elision markers
  "...[N characters elided]..." at the cut points. The <CURSOR> token is
  always inside the window.
- improve: see the three cases above (whole / local+500 / chunked).
- summarize: single call or sequential chunk summarization with a running
  summary (compaction), see above.
- All of this happens transparently inside job execution; no user action.

* Errors and logging
- *enslop-log* buffer, one timestamped line per event: queued, processing,
  applied, SKIP (with reason), error (with reason).
- LLM failure aborts the current job only; the queue continues.
- A job whose buffer was killed is skipped with a log entry.

* Out of scope / future work
- RAG (vision.org marks it future; the job/anchor design keeps every
  request's buffer + position recorded in the log, which is the seed for
  it).
- Hard request timeout, line-boundary chunking, undo grouping (each job
  is currently undo-able as a sequence of primitive edits), multiple
  models per job, token-exact budgets.

* Test plan (no live server available in this environment)
- ERT suite enslop-test.el. The fake LLM (installed via
  enslop-llm-function) pops canned responses in order and records every
  message list it was given, so tests can assert on both buffer effects
  and the prompts that were sent (context management, tag forcing, etc.).
- Covered: all insertion rules incl. middle-of-region and buffer
  start/end; region immutability; improve (region / whole-buffer / BUFFER
  tag / large-buffer local mode / chunked); stale-anchor skipping for
  insert and improve; summarize (region, chunked running summary,
  source buffer untouched); elision markers; queue FIFO ordering;
  repeated same-cursor inserts; response tag parsing.
