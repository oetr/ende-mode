#+TITLE: deslop Issues
#+STARTUP: overview

This file turns the repository review into an actionable engineering backlog.
Items are ordered by severity and then by recommended implementation order.

Severity meanings:

- Critical: credential exposure, data loss, or severe resource exhaustion is possible.
- High: concrete correctness bug or major lifecycle/design defect.
- Medium: important robustness, privacy, usability, or maintainability problem.
- Low: code quality, packaging, naming, or documentation improvement.

Unless an item explicitly says otherwise, preserve existing behavior outside the
described defect and add focused ERT coverage for the changed behavior.

* Security and data integrity

** DONE [Critical] Force credential-bearing and provider processes to run locally
:PROPERTIES:
:FILES: deslop-curl.el, deslop-codex.el, deslop-operations.el, deslop-project.el, deslop-test.el
:END:

*** Problem

=make-process= and =make-pipe-process= inherit =default-directory=.  When a
deslop command starts from a TRAMP buffer, Emacs file handlers may therefore run
=curl= on the remote machine rather than the user's local machine.

The generic curl entry point at =deslop-curl.el:232-271= does not bind
=default-directory= to a known local directory.  The direct OAuth refresh
process at =deslop-codex.el:454-501= has the same problem.  Codex generation at
=deslop-codex.el:1054-1101= ultimately uses the generic curl entry point.

This crosses an important trust boundary:

- The remote machine may receive source prompts intended for a local process.
- The OAuth refresh path sends the OpenCode refresh token through process stdin.
- The remote machine controls =PATH=, the =curl= executable, DNS, proxies, and
  certificate storage.
- Temporary curl configuration and response-header files are normally created
  locally.  A remote =curl= process may not be able to access those paths, or it
  may write to a different path with the same spelling.

*** Required implementation

1. Add one shared helper that returns a trusted local process directory.  It
   should be an existing local directory and must satisfy
   =(not (file-remote-p directory))=.
2. Bind =default-directory= to that directory around all provider-related
   temporary-file creation, =make-pipe-process= calls, =make-process= calls, and
   initial =process-send-string= calls where necessary.
3. Reject a remote =temporary-file-directory= or explicitly select a safe local
   temporary directory.
4. Decide and document the policy for source buffers whose
   =default-directory= is remote:
   - Supported policy: copy only the already constructed request body to a local
     process and never execute commands remotely.
   - Unsupported policy: signal a clear =user-error= before reading credentials
     or starting a process.
5. Apply the same policy to generic generation, provider discovery, Codex model
   probing, and Codex OAuth refresh.

Do not solve this by shell quoting.  The existing argument-list process API is
correct; the defect is process locality.

*** Acceptance criteria

- Starting any provider operation while =default-directory= is a TRAMP path
  never runs =curl= through a remote file handler.
- OAuth access and refresh tokens are never sent to a process executing on a
  remote host.
- Header and config files passed to =curl= exist on the same host as the process.
- ERT tests stub or instrument =make-process= and verify that its effective
  =default-directory= is local for generation, discovery, model probing, and
  refresh.
- The chosen remote-buffer policy is documented in the package documentation.

** TODO [Critical] Bound aggregate structured-edit growth before mutation
:PROPERTIES:
:FILES: deslop-edit.el, deslop-operations.el, deslop-core.el, deslop-test.el
:END:

*** Problem

Raw and normalized edit counts are bounded by
=deslop-max-write-anywhere-edits= and =deslop-max-normalized-edits=, but the
aggregate number of inserted characters is not bounded.  In particular,
=all: true= can expand one replacement string to thousands of applications.

A provider can return a moderately large =text= value and request that it be
inserted at up to 10,000 anchors.  The response remains within network limits,
but applying it may allocate an enormous buffer, block Emacs, or exhaust memory.
Because edits are currently committed one by one, interruption can leave a
partially modified source buffer.

Relevant code:

- Limits: =deslop-edit.el:19-31=
- =all: true= expansion: =deslop-edit.el:100-188=
- Application loop: =deslop-operations.el:448-487=

*** Required implementation

1. Add configurable positive limits for at least:
   - Aggregate replacement characters across all normalized edits.
   - Maximum projected buffer growth.
   - Maximum final buffer size after the pass.
2. After parsing and expansion, calculate all projected sizes before changing
   the target buffer.
3. Signal =deslop-edit-resource-error= if any limit would be exceeded.
4. Do not apply even the first edit when preflight validation fails.
5. Keep the existing count limits as separate defense-in-depth controls.
6. Prefer applying a complete validated pass in one =atomic-change-group=; see
   the separate transaction-semantics issue below.

Be careful with replacements: projected growth is the sum of
=(length text) - (end - start)=, while final size must not become negative and
must account for every normalized edit exactly once.

*** Acceptance criteria

- A small response expanded by =all: true= cannot exceed configured aggregate
  insertion, growth, or final-size limits.
- Limit failures leave buffer text and review overlays unchanged.
- Boundary values equal to the configured limit are accepted.
- Tests cover insertion-only edits, replacements that grow text, replacements
  that shrink text, and =all: true= expansion.

** TODO [High] Make closed-file change-set writes atomic and race resistant
:PROPERTIES:
:FILES: deslop-tools.el, deslop-project.el, deslop-test.el
:END:

*** Problem

=deslop-tools--apply-change-set-object= validates a digest and then overwrites a
closed file directly with =write-region= at =deslop-tools.el:601-642=.  There is
a time-of-check/time-of-use window between validation and writing.

Possible failures include:

- Another editor or process changes the file after digest validation and its
  work is overwritten.
- Emacs or the operating system stops during =write-region= and leaves a
  partially written file.
- The path is replaced with another filesystem object after validation.
- Existing file modes or other important attributes are lost by an incorrect
  temporary-file strategy.

*** Required implementation

1. Record file identity information before preparing the new content.  Include
   at least modification time, size, and a digest; use inode/device information
   where meaningful and available.
2. Write the complete new content to a temporary file in the target file's
   directory so the final rename is on the same filesystem.
3. Preserve the original file's mode.  Decide whether ownership, ACLs, extended
   attributes, and backups are in scope and document that decision.
4. Immediately before replacement, re-read or re-stat the original and reject
   the operation if its identity or content changed.
5. Atomically rename the temporary file over the original.
6. Delete the temporary file on every failure path.
7. Define explicit behavior for TRAMP files.  Do not assume local rename
   semantics apply to remote handlers.

*** Acceptance criteria

- Successful local writes replace the file atomically and preserve its mode.
- A simulated concurrent modification causes a clear failure and preserves the
  concurrent writer's contents.
- A failure before rename leaves the original file unchanged and removes the
  temporary file.
- Tests cover changed content, changed identity, mode preservation, and cleanup.

** TODO [High] Fix structured-repair accounting so unresolved edits cannot disappear
:PROPERTIES:
:FILES: deslop-operations.el, deslop-edit.el, deslop-history.el, deslop-test.el
:END:

*** Problem

Repair handling at =deslop-operations.el:599-635= replaces the complete prior
=:failures= list with the failures returned by the latest model response.
=deslop--structured-preserve-failure-indices= at
=deslop-operations.el:499-510= associates new and old failures by list position.

This is incorrect when a repair response omits or reorders edits.  For example:

1. The first pass has two failed edits, A and B.
2. The repair response contains only a successful repair for A.
3. The second pass reports no failures.
4. B disappears from state and is counted as neither repaired nor skipped.

Reordering two failed repairs can also assign their original indices to the
wrong edits.

*** Required implementation

1. Assign a durable identity to every failed edit from the original response.
   A numeric original edit index is sufficient if the repair protocol requires
   the model to return it explicitly and validates it.
2. Include each durable identity in the repair prompt and schema.
3. Require repair responses to identify which original failure they address.
4. Maintain a map or equivalent state keyed by durable identity.
5. Remove a failure only after its identified repair applies successfully.
6. Retain failures omitted by a repair response.
7. Reject duplicate, unknown, or already-resolved repair identities without
   corrupting counters.
8. Ensure =:requested=, =:first-pass-applied=, =:repaired=, =:skipped=, and
   =:final-failures= remain mathematically consistent.

*** Acceptance criteria

- An omitted repair remains in =:final-failures= and counts as skipped.
- Reordered repairs retain correct original indices.
- A partial repair updates only the addressed failure.
- Duplicate and unknown repair IDs produce explicit diagnostics.
- History reports every unresolved original edit exactly once.

** TODO [High] Make terminal callback failures observable
:PROPERTIES:
:FILES: deslop-transport.el, deslop-llm.el, deslop-codex.el, deslop-test.el
:END:

*** Problem

=deslop-transport-session-settle= marks the transport session terminal before
invoking =:on-done= at =deslop-transport.el:89-112=.  Both concrete transports
also mark their own session terminal first:

- =deslop-llm.el:83-105=
- =deslop-codex.el:780-797=

If =:on-done= signals, =deslop-transport-session-invoke= calls the configured
callback-error handler.  That handler attempts to fail an already-terminal
session, so nothing happens.  The exception is swallowed and =:on-error= is not
notified.

*** Required implementation

1. Separate transport settlement from callback dispatch.  A callback exception
   must not attempt to settle the transport a second time.
2. Define one explicit callback-error contract.  Reasonable choices include:
   - Invoke a separate =:on-callback-error= callback.
   - Report through a package error hook and =display-warning=.
   - Let terminal callback errors propagate after resource cleanup.
3. Ensure resource cleanup and single transport settlement remain guaranteed.
4. Apply identical behavior to generic and Codex transports.

*** Acceptance criteria

- An =:on-done= callback that signals produces an observable callback error.
- Resources are cleaned exactly once.
- =:on-done= and transport settlement are not repeated.
- An =:on-error= callback that itself signals cannot recurse indefinitely.

** TODO [High] Define transaction and partial-success semantics for structured edits
:PROPERTIES:
:FILES: deslop-operations.el, deslop-queue.el, deslop-history.el, deslop-review.el, deslop-test.el
:END:

*** Problem

=deslop--structured-edit-pass= applies each valid edit independently at
=deslop-operations.el:448-487=.  Each individual edit is atomic, but the pass and
overall operation are not.  Successful edits remain in the buffer if a later
edit fails or the repair transport fails.  The job may end in =failed= even
though it changed the source buffer.

The current states =completed= and =failed= do not communicate whether changes
were applied.  History has a "COMPLETED WITH WARNINGS" display string, but that
is not represented in the scheduler state model.

*** Required implementation

1. Decide the product behavior explicitly:
   - Transactional: preflight every edit and apply the complete pass atomically.
   - Partial success: retain applicable edits and represent that outcome in job
     state and user-visible status.
2. If transactional, validate current anchors, overlap, review availability,
   growth limits, and writability before entering one =atomic-change-group=.
3. If partial success, add a terminal state such as =completed-with-warnings= or
   a separate structured outcome field.  Do not label a buffer-changing result
   as an undifferentiated failure.
4. Ensure queue status, history, mode-line counts, and event consumers understand
   the chosen state.
5. Document whether repair-network failure rolls back already applied edits.

*** Acceptance criteria

- The chosen semantics are documented and consistent across queue state,
  history, messages, and review overlays.
- A failure in edit N cannot produce an undocumented partial mutation.
- Tests cover first-pass partial failure, repair failure, user quit, read-only
  buffers, and review-overlay creation failure.

* Privacy and review model

** TODO [High] Clarify or redesign review-before-application semantics
:PROPERTIES:
:FILES: deslop-operations.el, deslop-review.el, deslop.el, deslop-test.el
:END:

*** Problem

Ordinary insert, improve, and structured operations mutate the live source
buffer before the user approves them:

- Plain result application: =deslop-operations.el:297-379=
- Structured result application: =deslop-operations.el:448-487=
- Review overlays: =deslop-review.el:216-255=

The overlay is rollback metadata, not a security approval gate.  The user can
save the buffer while reviews are pending.  A compromised provider can insert
arbitrary source or file-local-variable text that is present immediately and
may be saved accidentally.

*** Required implementation

Choose and document one model:

1. Staged review: render a diff or indirect buffer and apply changes only after
   explicit approval.  This is the safer default for remote providers and
   whole-buffer edits.
2. Immediate application: preserve current behavior, but call it out clearly in
   the UI and documentation.  Add an optional save warning when pending reviews
   exist and consider confirmation for remote or whole-buffer operations.

If staged review is selected, preserve source markers/digests so approval fails
cleanly when the source changes before application.

*** Acceptance criteria

- The UI and docs accurately state whether generated text has already changed
  the source buffer.
- The user cannot unknowingly save pending generated output under the chosen
  default workflow.
- Remote and whole-buffer operations receive an appropriately strong review
  boundary.

** TODO [High] Use privacy-preserving history defaults and a byte budget

- Default history does not retain complete source prompts or reasoning.

- Privacy behavior is documented next to remote-provider setup.

** TODO [Low] Replace filename denylisting with explicit future tool capabilities
:PROPERTIES:
:FILES: deslop-project.el, deslop-tools.el, deslop-test.el

*** Problem

=deslop-project-excluded-path-patterns= at =deslop-project.el:28-39= excludes a

  timer, hook, or callback state.

* Recommended implementation order

The following order minimizes rework:

1. Force all provider processes to run locally.
2. Bound aggregate structured-edit growth.
3. Fix structured-repair identities and unresolved-failure accounting.
4. Protect selector buffer ownership and fix model-probe callback arity.
5. Choose transaction and review-before-application semantics.
6. Centralize lifecycle ownership and simplify transport session ownership.
7. Make closed-file writes atomic and bound project traversal.
8. Change privacy defaults for history and rejected output.
9. Make project tools and Codex integration optional/lazy where possible.
10. Improve selector, review navigation, faces, and discovery diagnostics.
11. Clarify public APIs, dependencies, naming, and Customize groups.
12. Add documentation, split tests, add CI, and reorganize into =lisp/=,
    =test/=, and =docs/=.

* Existing strengths to preserve

These parts are well designed and should not be lost while addressing the
issues above:

- Lexical binding and consistent =deslop-= package prefixing.
- Use of =cl-defstruct= for jobs, targets, sessions, history, and change sets.
- Queue callbacks bind their originating job instead of trusting mutable global
  current-job state.
- Target markers, source digests, original narrowing, and buffer-local mutation
  hooks handle many stale-target cases carefully.
- Normal cancellation and settlement are generally idempotent and use
  =unwind-protect= appropriately.
- Processes use argument lists rather than a shell, avoiding ordinary shell
  injection and quoting problems.
- Bearer and refresh tokens are kept out of process argument lists.
- Provider URLs and request headers receive unusually strong validation.
- JSON network keys are parsed into hash tables without interning untrusted
  symbols.
- Response, SSE, stderr, header, and several output resources already have
  configurable safety limits.
- Review rejection uses atomic buffer changes and restores original text
  properties.
- The existing 150 ERT tests cover many subtle parser, queue, cancellation,
  stale-callback, overlay-boundary, and authentication cases.
