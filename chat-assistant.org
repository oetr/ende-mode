#+STARTUP: overview

* Final Design
Provide a chat workflow inside ende without preventing the user from writing and editing ordinary Org content.
Use an ordinary Org buffer for chat, with top-level headings defining independent conversation roots.
Message ownership is such that sections marked as assistant by properties, are also sent as such to the server.
Section marked as such, assumes that all of its content is also marked as such.
Unmarked content is assumed to be user content.
Content marked as "hidden" are always hidden.
Content marked as "reasoning" are hidden by default, but user can configure them to be sent.

Generated Org content is parsed and normalized before it is inserted, so its headings cannot accidentally change the outer conversation structure.

* Refined text
Each message should have a host-created wrapper with stable turn and reply identifiers, role, origin, lifecycle state, and edited status.
A generated response is parsed in a temporary Org buffer, stripped of reserved control metadata, and inserted beneath one assistant wrapper after uniform heading normalization.
Plain-text responses are accepted without requiring headings, and malformed or unsafe fragments are retained in a readable inert form with a diagnostic.

Context serialization should follow document order within the active root and include only eligible, completed turns plus explicitly included reference material.
The current question's body must be included while existing replies and future content are excluded according to a precisely defined endpoint.
A context preview should show roles, included sections, exclusions, private material, and estimated size before transmission.

Provide commands for asking, creating a root, marking roles or references, following up, previewing context, validating the buffer, retrying, and canceling.
Follow-up should create a correctly placed draft without sending it.
Resending must have explicit replace, retain, or alternative semantics.

Requests should snapshot their messages and destination identifiers, then revalidate the destination before atomically inserting a validated reply.
Editing, refiling, cancellation, failure, partial output, save/reopen, and duplicate identifiers must have visible states and recovery paths.
Keep provider reasoning out of future context by default, and preserve ordinary Org editing without silently changing bindings or executing generated Org constructs.

* Design Goal

Provide a simple chat workflow inside ende without preventing the user from
writing and editing ordinary Org content.

The chat document is an ordinary Org document.  Its outline is used for
navigation and context selection, while explicit metadata identifies
conversation turns.  Generated Org content is parsed and normalized before it
is inserted, so its headings cannot accidentally change the outer conversation
structure.

** Review: overall assessment

The direction makes sense: an ordinary, editable Org file with explicit sends
and explicit message metadata is a strong foundation for an Emacs interface.
It is not yet a comfortable implementation contract.  Message ownership,
reference overrides, reply placement, and asynchronous editing have unresolved
ambiguities that could silently send the wrong context.  Those are trust and
usability problems, not merely implementation details.

The walkthrough at the bottom is a hypothetical power-user simulation, not a
report of testing an existing mode.  The annotations below identify the points
where that workflow would succeed or become confusing.

* Outer Document

The outer document uses normal =org-mode= editing and navigation.

Top-level headings delimit independent topics or chat roots.  Content from an
earlier top-level heading is not included when asking a question in a later
top-level heading.

** Review: useful isolation, but ordinary outline edits change context

This is easy to understand and provides valuable topic isolation.  However,
a power user routinely promotes, demotes, and refiles headings.  Promoting a
follow-up to level one would silently discard its prior conversation context;
refiling a heading could silently introduce unrelated history.  Keep this rule
if desired, but show the active root and message count before sending and offer
a context-preview command.  Document that root membership follows the current
outline, not the original conversation.  Define what happens before the first
heading and when the root itself is an unmarked topic container.


Conversation headings carry explicit properties:

#+begin_src org
* Q: How can we use bash?
:PROPERTIES:
:ENDE-CHAT-ROLE: user
:ENDE-CHAT-STATE: sent
:ENDE-CHAT-TURN: 1
:END:
What is the best way to use bash on Linux?

** A: Start with the shell
:PROPERTIES:
:ENDE-CHAT-ROLE: assistant
:ENDE-CHAT-ORIGIN: llm
:ENDE-CHAT-STATE: complete
:END:
#+end_src

The role property is authoritative.  Heading depth alone never creates a
conversation message.

* Message Boundaries

An explicit role annotation creates a message boundary.

Unmarked content is not silently interpreted as a user or assistant turn.  It
is preserved as raw Org reference material and included in the request when it
falls inside the selected context.

Role inheritance follows these rules:

1. An explicit role applies to its heading and content.
2. Unmarked descendants inherit the enclosing role.
3. A deeper explicit role overrides the inherited role.
4. A role never propagates upward to unmarked ancestors.
5. A role never propagates sideways into later siblings.

** Review: ownership and inheritance need a precise serialization rule

This conflicts with the later promise that new unmarked content remains
reference or draft content.  In this model, an ordinary note typed inside an
assistant subtree becomes assistant context.  That may be a reasonable default,
but it must be stated plainly and shown at point.

Define each explicit message as owning its heading/body and unmarked
descendants, excluding independently marked subtrees.  Then resolve the hard
case: an assistant body, a nested user question, and more assistant-owned text
after that question.  Preserving textual order would split the assistant into
two messages; aggregating it into one would reorder content.  The present
one-response/one-message invariant cannot handle arbitrary interleaving without
an additional constraint.  Prefer complete message subtrees arranged as
siblings under a topic, with follow-ups after the response subtree.  If nested
turns are supported, specify and test their exact ordering and ownership.

Also define an explicit reference override that stops role inheritance.
Absence of a property cannot mean both 'inherit assistant' and 'explicitly
reference'.  =ende-chat-mark-reference= needs a durable representation.


If an assistant annotation appears below several unmarked headings, the
unmarked ancestors remain reference material.  They are not retroactively
turned into an assistant message.

The API has no reference role.  Reference material is therefore carried in a
user message with an explicit instruction that it is reference, not a
conversation turn:

#+begin_src text
The following is unmarked Org reference material.  Preserve its structure,
but do not answer it unless the current marked question asks you to.

* Notes
** An unmarked section
*** More notes
#+end_src

An assistant annotation without any preceding user question is an orphan
assistant message.  The permissive behavior is to send the preceding material
as a reference message and retain the assistant message.  The interface should
warn about the orphan rather than inventing a question.

** Review: reference is context, not a security boundary

The reference wrapper is useful for communicating intent, but its instruction
cannot guarantee that the model will not answer or follow instructions in the
reference text.  Delimit reference material clearly and put the policy for
handling it in trusted system instructions.  Do not describe reference-only as
a behavioral guarantee.  Reference text can also contain private notes; show
exactly what will leave the buffer, including drawers and hidden subtrees.

For an orphan with no preceding material, do not synthesize an empty reference
message.  Check provider constraints and issue an actionable diagnostic with
options to reclassify, exclude, or send if supported.  A warning should appear
before transmission, not merely in a log afterward.


* Model Responses

The model is asked to return an Org-mode fragment.  The response is never
inserted directly into the chat buffer.  It is parsed first, then sanitized and
shifted to fit the section in which it will be inserted.

All actual headings in the normalized response are part of one assistant
message.  They do not create additional conversation turns merely because
they have Org heading syntax.  A new question requires an explicit user role
annotation or the question command at that heading.

If the user edits a generated response, it remains assistant context.  The
message can additionally be marked as user-edited without changing its role.

** Review: preserving assistant attribution is exceptionally good

Keeping an edited answer as assistant context avoids a surprising role change
when the user fixes a typo or trims an answer.  Show an edited indicator and
explain that future requests use the current edited text, not the original
model response.  An optional original-response snapshot would help users
recover accidental edits without requiring character-level provenance.

* Context Selection

When the user asks a question, ende finds the active top-level chat root and
serializes the document in textual Org order up to the current question.

The context includes:

- The active top-level root.
- Earlier marked user and assistant turns in that root.
- Unmarked Org reference content in its original Org form.
- The current marked user question.

The context excludes:

- Earlier top-level roots.
- Content after the current question or selected subtree.
- Future sibling questions and answers.

This is a prefix-history model.  A follow-up question and answer that appear
before a later question are included in the later question's context.

** Review: prefix history is coherent, but looks like branching when it is not

A power user will often read sibling questions as alternative branches.
Here, earlier siblings influence later ones.  Label this explicitly as
'linear history within this topic' in help and context preview.  For the first
version, a clear command to copy a question into a new topic is preferable to
an implicit or incomplete branching feature.

'Up to the current question' needs an exact endpoint: the heading alone, its
body, or its owned subtree?  Sending only the heading loses the prompt body;
sending the entire subtree can include an old answer or nested future turns.
Specify that the current question's owned content is included and which
existing replies are excluded on resend.  Define what 'selected subtree'
means, since no command here selects one.

Drafts, failed sends, and canceled replies also need inclusion rules.  The
example has =sent= and =complete= states, but serialization currently ignores
state.  Never silently include an earlier unsent draft as conversation history.
Add a context preview showing ordered roles, included sections, exclusions,
and estimated size.  When context exceeds the model limit, ask the user to
narrow it rather than silently truncating history.


For example:

#+begin_src org
  ,* Q: Main question
  ,** A: First answer
  ,*** Q: Follow-up question
  ,*** A: Follow-up answer
  ,** Q: Second question
#+end_src

** Review: this example is not executable under the stated rules

None of the example headings has a role property.  As written, these are
reference headings, not user and assistant turns; =Q:= and =A:= are explicitly
not authoritative.  Label this a schematic example with metadata omitted, or
provide a companion example containing the actual property drawers.  Include
one unmarked note and one explicit reference override so readers can predict
the real serialization, rather than infer a second rule from the prefixes.

The request for =Second question= is serialized as:

#+begin_src text
  system: ende chat instructions
  user: Main question
  assistant: First answer
  user: Follow-up question
  assistant: Follow-up answer
  user: Second question
#+end_src

The Org headings and nested response structure remain in each message's
content where applicable.  The wire format is linear; the outer Org tree is
used to determine that order and the context boundary.

* Reply Parsing and Normalization

The model is instructed to return only Org-mode syntax, with one or more
top-level sections for the response.  The response is first parsed in a
temporary Org buffer.

The parser must:

1. Recognize actual Org headlines without treating stars inside source blocks,
   example blocks, drawers, or comments as headlines.
2. Find the shallowest (highest) and deepest (lowest) actual headline levels.
3. Shift every response headline by the same amount so that the shallowest
   response headline becomes the first valid subsection of its insertion
   context.
4. Preserve the relative depth between all response headlines.
5. Preserve non-headline Org syntax and text.
6. Ignore or replace any conversation-role metadata emitted by the model.
7. Reject or safely wrap malformed responses that contain no usable headline.

** Review: accept simple answers and specify the actual outer boundary

A useful answer such as 'Yes, use bash -n script.sh' need not have a heading.
No heading does not make an Org fragment malformed.  Accept ordinary text and
wrap it in a host-created assistant heading.  Avoid forcing verbose sections
for a one-line response.

Use one host-created assistant wrapper with authoritative properties, and put
all generated headings strictly below it.  Otherwise, a response with multiple
shallowest headings becomes several siblings, and a property on the first
cannot own the others.  With a wrapper, =target-level= must mean the wrapper's
first child level, not the reply wrapper level itself.  Preserve any preamble
before the first generated heading inside that wrapper as well.

Parsing must follow actual Org syntax rather than a blanket assumption about
stars in 'comments' or 'drawers'.  Test COMMENT subtrees, valid blocks,
unterminated blocks/drawers, and heading-like text in each context against the
supported Org version.  For unsafe fragments, retain a readable inert fallback
and a diagnostic instead of losing the answer.  Ensure fallback delimiters
cannot themselves be closed by arbitrary response text.


Let =response-min-level= be the shallowest response headline level and
=target-level= be the level required by the containing conversation section.
The uniform shift is:

#+begin_src text
delta = target-level - response-min-level
#+end_src

For every actual response headline with level =level=, insert it at
=level + delta=.  The deepest level is useful for validation and resource
limits, but every response section receives the same shift.  Stars inside
source blocks, example blocks, drawers, comments, and literal text are not
headings and are never shifted.

The complete normalized response, regardless of how many Org headings it
contains, receives one assistant origin and one assistant message boundary.

** Review: structural normalization is strong, but is not a full sanitizer

Uniform shifting preserves the answer's internal outline: this is an excellent
fit for Org navigation.  Add tests for preambles, multiple top-level response
sections, very deep headings, and attempts to emit control properties.

Define which metadata is stripped: all reserved ende control fields, not
just role, including origin, state, IDs, and any inheritance overrides.
Generated content must never gain authority merely by resembling a drawer.
Treat generated Babel blocks, links, includes, and other active Org constructs
as untrusted content.  Do not execute, follow, or export them automatically;
retain normal confirmation safeguards.  'Sanitized' should name concrete
structural guarantees, not imply that generated Org is safe to execute.


* Editing and Provenance

The outer role and origin properties are control metadata, not instructions
that the model can create or change by emitting text.

The intended provenance states are:

- =user=: explicitly authored or explicitly marked as a question.
- =assistant=: generated by the LLM and used as assistant context.
- =reference=: unmarked Org content that is included as raw context.
- =edited=: content originally generated by the LLM but modified by the user.

Editing an assistant response does not turn it into a user message.  If the
user wants a section to become a question, an explicit command marks it as a
user turn.

Adding or deleting Org sections must not change the role of neighboring
sections.  New unmarked content remains reference or draft content until the
user explicitly classifies it.

Exact character-level history is not required for the first implementation.
The durable boundary is the marked heading or normalized response region, with
an edited state for user modifications.

** Review: use durable fields with separate meanings

The listed provenance states mix role, origin, classification, and modification.
Define them independently: API role (user/assistant), immutable origin
(user/llm), an edited flag, lifecycle state (draft/pending/complete/etc.), and an
explicit reference classification.  Specify whether title changes and property
maintenance count as edits; merely inserting the initial reply must not mark
it user-edited.

A 'normalized response region' must survive save/reopen, undo, and refiling.
A host-created wrapper with persistent properties is clearer than an invisible
in-memory span.  Use stable turn IDs and reply-to IDs rather than relying on
=TURN: 1= or position.  Detect duplicated IDs after copy/paste and offer repair.
Deleting a role drawer or refiling a child under another message can change
ownership; provide validation and visible diagnostics rather than promising
that arbitrary Org edits can never affect classification.


* Interaction

The proposed commands are:

- =ende-chat=: open or create the chat Org buffer.
- =ende-chat-ask=: send the marked question at point.
- =ende-chat-new=: create a new top-level chat root.
- =ende-chat-mark-question=: mark the current section as a user question.
- =ende-chat-mark-assistant=: attribute the current section to an assistant
  response.
- =ende-chat-mark-reference=: explicitly keep content as raw reference.
- =ende-chat-cancel=: cancel the active request.

Return remains ordinary Org editing.  Sending is explicit so that a heading
such as =*** Section= is not mistaken for a question merely because it was
inserted by the user.

** Review: excellent editing default; the common follow-up is still too manual

Leaving Return alone respects muscle memory and is one of the best decisions
here.  Keep standard Org navigation, folding, capture, and source-block editing.

The simulated user finishes reading an answer and wants to ask a follow-up.
Currently they must find a safe insertion level, create a heading, mark it, and
send it.  Add =ende-chat-follow-up= to create an empty, correctly placed draft
user turn and move point to its body.  Specify =ask= behavior in a question
body, inside an assistant subtree, on reference text, and with an active
region.  Do not unexpectedly mark and send arbitrary surrounding content.

Add discoverable commands for preview-context, validate-buffer, retry, and
explicit resend/replace.  Define whether resending retains, replaces, or
creates an alternative to an existing answer, and how that affects later
context.  Show role, root, request state, and edited status unobtrusively; do
not require users to inspect property drawers for every interaction.


The suggested minor-mode binding is =C-c e c=.  The existing =C-c e= binding
must become a prefix map for this sequence to work.

** Review: do not silently take over an existing binding

Changing =C-c e= into a prefix can break the user's existing command.
Letter-based =C-c= bindings are conventionally reserved for users.  Offer a
customizable prefix map and documented example bindings rather than installing
this takeover by default.  All operations should remain available through
=M-x=; check existing ende conventions before choosing packaged bindings.


* Transport Mapping

The existing ende transport already accepts role-tagged messages.  Chat
requests use:

#+begin_src text
system    fixed chat and Org-format instructions
user      marked question or reference context
assistant previous marked assistant response
user      next marked question
assistant current generated response
#+end_src

There is no separate =agent= role.  Thinking output is either omitted from
future context or retained inside the same assistant message; it does not
create a separate assistant turn.

** Review: distinguish request history from the response

The final 'assistant current generated response' is output, not part of the
request currently being sent.  Make that distinction explicit and use provider
adapters for constraints such as adjacent messages of the same role.

Do not casually retain thinking output as answer content.  Default to omitting
provider reasoning events from future context, and respect provider-specific
handling of opaque reasoning data.  If a provider exposes a user-visible
summary, keep it distinct from the answer and make inclusion intentional.


* Main Invariants

- Ordinary Org editing must remain possible.
- Heading depth alone must never determine message role.
- Model-generated Org headings must never escape their response boundary.
- One marked assistant response produces one assistant API message.
- Unmarked Org remains visible, structurally intact, and reference-only.
- New conversation turns require explicit user intent.
- A new top-level heading starts a new context root.
- Context order follows document order up to the current question.

* Implementation Shape

The first implementation can remain within the existing ende architecture:

- Add a chat buffer and command layer using ordinary =org-mode=.
- Add role/provenance properties and context serialization.
- Add a temporary Org response parser and uniform heading normalizer.
- Sanitize and rebase assistant responses before inserting them into the outer
  Org document.
- Reuse the existing provider snapshots, queue, cancellation, and normalized
  streaming events.
- Keep the transport message builder separate from the Org document parser.

** Review: asynchronous editing is a first-class design requirement

Reusing transport infrastructure is sensible, but it does not define buffer
behavior.  A power user will keep editing, move the question, switch buffers,
or kill the chat buffer while a request runs.  Snapshot the exact outgoing
messages and identify the destination by stable ID.  Revalidate the destination
before committing a reply; never insert at whatever point happens to be current.
If it was deleted or ambiguously duplicated, preserve the reply in a recovery
buffer and ask where it belongs.

Because replies must be parsed before insertion, show streaming progress in a
separate preview/status area, then commit the validated result atomically.
Do not jump point, steal the selected window, or unfold unrelated sections on
completion.  Make final insertion one undoable operation and explain that undo
does not cancel a network request.  Cancellation, failure, partial output, and
retry need explicit states; incomplete replies should be excluded from future
context unless deliberately accepted.  Define concurrency scope and which
request =cancel= targets when more than one is pending.

The critical boundary is between the Org document representation and the
linear role-tagged message list sent to the provider.

* Simulated power-user walkthrough and verdict

This is a thought experiment using the written specification, not an executed
usability test.  Alex is an experienced Emacs user who relies on Org folding,
refiling, keyboard navigation, and editing while background processes run.

1. Alex runs =M-x ende-chat=, creates a topic for shell scripting, and pastes
   notes containing source blocks.  Ordinary Org editing feels immediately
   familiar.  Explicit sends mean pressing Return cannot accidentally transmit
   unfinished text.  This is a substantial advantage over many chat interfaces.

2. He writes a question below his notes, marks it, and invokes =ask=.  He wants
   to inspect what will be sent, particularly folded notes and property
   drawers.  The current command list provides no context preview.  He cannot
   confidently distinguish reference context from excluded private notes.
   A preview and visible active-root indicator would resolve this hesitation.

3. The answer contains a preamble, two peer sections, and a Bash block.  He
   folds one section and reads the other.  The uniform depth shift is useful,
   but only a single enclosing assistant wrapper makes ownership of both peer
   sections clear.  Without that wrapper, the specification does not explain
   where the answer actually ends.

4. He corrects a command in the answer.  Retaining assistant attribution with
   an edited indicator feels right.  He then types 'Check this on the server'
   as a child note.  Under role inheritance this becomes assistant context,
   contrary to the promise about new unmarked content.  An explicit reference
   override and an at-point classification indicator are necessary here.

5. He wants a follow-up about quoting.  Manually choosing a safe heading level
   and adding metadata interrupts his flow.  A follow-up command should create
   a draft after the complete answer subtree, leaving point in its body.  It
   should not send until he explicitly invokes =ask=.

6. He creates another sibling question, expecting a fresh alternative.  Prefix
   history also sends the previous follow-up.  The model is internally coherent,
   but the visual tree suggests branching.  Help, preview, and an explicit
   'start new topic from this question' operation must make this distinction
   discoverable before it produces a misleading answer.

7. While a long answer is running, he refiles the question and edits another
   topic.  The desired behavior is a quiet completion at the identified turn,
   with no cursor jump.  The current design does not guarantee this.  Stable
   IDs, a request snapshot, destination validation, and a recovery path are
   required before background operation is trustworthy.

8. He cancels a request, retries it, then saves and reopens the file.  He expects
   canceled fragments not to enter future context, retries not to duplicate
   history silently, and all message boundaries to survive reopening.  These
   lifecycle rules need specification and automated tests, not user guesswork.

** Is it comfortable? Is it good?

The core is good: ordinary Org, explicit intent to send, topic isolation,
preserved answer structure, and stable attribution after edits all serve real
users.  Comfort is not yet established.  The unresolved ownership rules can
misattribute notes; the outline can imply nonexistent branches; and ordinary
editing during requests can threaten reply placement.

For a first usable version, prioritize one durable wrapper per message,
precise context endpoints and state filters, explicit reference overrides,
context preview, a follow-up command, and robust asynchronous insertion.
Keep branching and character-level history out of scope rather than offering
ambiguous partial versions.  Test the eight steps above with real Org users,
including save/reopen, undo, promotion, refiling, malformed replies, and
cancellation.  The practical acceptance criterion is that users can predict
what will be sent and where the answer will go without reading raw metadata.
